# Design Principles — AI Canvas Portfolio

実装時に必ず全項目を確認すること。

---

## 根本テーマ

**「既存のHTML/CSSの制約から解放された近未来のUXを実現する」**

HTMLは文書マークアップ言語として生まれた。CSSは文書を装飾する仕組みとして生まれた。
Webの全技術スタックは「テキスト文書をレンダリングしリンクする」ために設計されている。

このポートフォリオはその遺産を拒否する。問いかけるのは:
**「AI・GPU・空間コンピューティングが前提の今日、デジタル体験をゼロから設計したらどうなるか？」**

ただし「見た目が未来的」であることと「UXが未来的」であることは全く別の問題である。
宇宙的なビジュアルは手段であり目的ではない。
**従来のサイトよりも実際に便利で、直感的で、賢い体験**を提供して初めて「近未来のUX」と呼べる。

---

## HTML/CSSが課してきた制約の分析

何から「解放」するのかを明確にしなければ、解放は実現できない:

| 制約 | 由来 | 本プロジェクトでの解放 |
|------|------|----------------------|
| **ページ** | 紙の本 | → 1ビューポートの空間。ページ遷移なし |
| **スクロール** | 巻物（scroll） | → 空間内のテンプレート遷移で情報を切り替え |
| **矩形ボックス** | 活版印刷のブロック | → 有機的・不規則な形状とレイアウト |
| **フロー配置** | 上→下、左→右の文書構造 | → 放射状・空間的・文脈的配置 |
| **ナビゲーション** | 目次→章のリンク構造 | → 対話と行動観察による意図ベースの遷移 |
| **静的レンダリング** | 印刷物の模倣 | → 常に呼吸する生きたインターフェース |
| **均一なレイアウト** | テンプレート印刷 | → AIが毎回異なる見せ方を選択 |
| **フォーム入力** | 紙の書類のデジタル化 | → 自然言語による意図表現 |
| **テキストによる説明** | 文書文化 | → 図形・アイコン・空間配置・動きで意味を伝える |
| **受動的なUI** | ユーザーが操作→システムが応答 | → サイトがユーザーの行動を観察し先回りする |

この表は「なぜそうなっているか」を問い続けるための道具である。
実装中に「この表現は技術的制約による妥協では？本来どう見せたい？」と自問すること。

## コア原則

### 1. 見せる、説明しない

**文章で説明しなければ伝わらないなら、それはデザインの失敗。**

モニターは光を発する平面であり、文字を表示するためだけの装置ではない。
図形、色、動き、配置、サイズ — これらすべてが情報伝達の手段。

- 「ここに質問を入力してください」とテキストで書く代わりに、入力欄の視覚的な存在感・脈動・グローで「ここが対話の起点だ」と直感させる
- スキルの習熟度を文字で「上級」と書く代わりに、円の大きさや輝度で表現する
- プロジェクトの重要度をリストの順番で示す代わりに、空間上の位置・サイズ・動きの強さで表現する
- 操作のヒントはテキストラベルではなく、要素の振る舞い（引力、反応、変形）で示す

### 2. 行動を観察し、先回りする

**ユーザーが「何をすればいいかわからない」と思った瞬間、それはサイトの失敗。**
しかしその失敗に対する解決策は「説明文を追加する」ではない。
**サイト自身がその迷いを検知し、インタラクティブに助ける**のが近未来のUX。

具体的な行動シグナルとサイトの応答:

| ユーザーの行動 | 推測される状態 | サイトの応答 |
|---|---|---|
| 3秒以上何も操作しない | 何をすればいいかわからない | 入力欄を軽くパルスさせる。さらに待つと周囲にヒントとなるキーワードが浮かび上がる |
| カーソルが特定の要素の近くに留まる | その要素に興味がある | 関連情報をさりげなく展開する、詳細がプレビューされる |
| 素早くカーソルを動かしている | 何かを探している | 主要なインタラクションポイントをハイライトする |
| 入力欄にフォーカスしたが打たない | 何を聞けばいいか迷っている | 例示的なキーワードをサジェストとして浮かべる |
| 同じ領域を繰り返し見ている | もっと情報がほしい | その領域の情報密度を上げる、または関連トピックを提示 |

この原則は「押しつけがましいポップアップ」とは根本的に違う。
ポップアップは画面を遮る。ここで言う応答は環境の変化 — 光の強さが変わる、要素が近づいてくる、新しい要素がゆっくり出現する — であり、空間に溶け込む形で行う。

### 3. AIがインターフェースそのものである

メニュー、ボタン、リンク — これらは人間がコンピュータに合わせるためのUIだった。
AIが仲介する世界では、ユーザーは意図を伝えるだけでよい。

- ナビゲーションは「会話」で行う
- 同じ質問でも文脈・回数によって異なるテンプレートで応答する
- 操作方法を事前に学ぶ必要がない（ゼロ学習コスト）
- **AIは受け身ではない** — ユーザーの行動を観察し、必要なら自ら語りかける

### 4. 空間で思考する、文書で思考しない

情報は「上から下に読む文書」ではなく「空間に存在するオブジェクト」として扱う。

- 1ビューポートに全情報を空間配置。スクロールに逃げない
- 奥行き（perspective、parallax、depth layers）で空間を構築する
- 要素の配置自体が意味を持つ（中心＝主役、周辺＝文脈、近い＝関連性高い）
- 背景環境（グラデーションメッシュ、パーティクル、軌道リング）が「場」を作る
- モニターは文書を表示する装置ではなく、**光と動きで情報を伝える空間**

### 5. 矩形を疑う、ただし教条的に排除しない

カード、セクション、グリッド — これらは全てボックスモデルの産物。
しかし表形式のデータに表を使い、リストにリストを使うのは合理的。

- **空間配置・装飾・レイアウト**: 放射状・不規則・有機的を優先
- **コンテンツ表示**: 可読性を最優先。テーブルやリストが最適なら矩形を使う
- 判断基準: 「この矩形はボックスモデルの惰性か、それとも情報の最適な器か？」

### 6. 呼吸するインターフェース

「アニメーション付きサイト」ではなく「生きているインターフェース」を作る。
この二つの違いは本質的:

- **アニメーション付きサイト**: 静的なサイト + 装飾としてのモーション
- **生きているインターフェース**: 動き自体がサイトの存在形態

具体的に:
- 生命のリズム: 呼吸のような周期的な脈動、微細な揺らぎ
- 環境への反応: マウス位置、時間経過、インタラクション状態に応じた変化
- **静寂も設計する**: 呼吸には吸と吐がある。全要素が常に動き続けるのは痙攣であり生命ではない
- 背景パーティクル・グロー・グラデーションが協調して「場の空気」を作る

### 7. 毎回異なる体験を提供する

従来のサイトは何度訪問しても同じ画面を返す。それは印刷物の思想。
このサイトは訪問のたびに異なる体験を提供する。

- 30+ テンプレートによるビジュアルバリエーション
- VisualSeed による色・レイアウト・アニメーションタイミングの乱数化
- AIの応答内容自体が文脈により毎回変化
- テンプレート遷移の多様性（clipExpand, slideOver, scaleBlur, verticalSplit）

### 8. 情報は知性的に提示する

「全部見せる」のは図書館。「何も見せない」のはブラックボックス。
AIが文脈に応じて最適な量と形式を選ぶのが近未来のUX。

- 質問に対して必要十分な情報を、最適なテンプレートで提示
- スキル一覧のように密度が求められる場面では密に
- 価値観のようにストーリーが大事な場面では余韻を持たせて疎に
- 余白は「空虚」ではなく「呼吸の間」として機能させる

## Welcomeの設計思想

初回訪問時のWelcomeは、このサイトの全原則が試される最重要場面。

### やってはいけないこと
- 「質問を入力してください」とテキストで説明する
- 使い方ガイドやチュートリアルを表示する
- 従来のヒーローセクション（キャッチコピー + CTAボタン）を作る

### 求められること
- **入力欄の存在が視覚的に自明** — グロー、脈動、空間的な存在感で「ここが起点」と直感させる
- **迷ったら助ける** — 数秒間操作がなければ、周囲にキーワード（Projects, Skills, Career...）がゆっくり浮かび上がる。クリック可能だが、あくまで「浮遊する存在」であり「メニューボタン」ではない
- **世界観の提示** — パーティクル、グラデーション、軌道リングで「ここは普通のサイトではない」と伝える。これは背景環境（TemplateShell）が担う
- **最初のインタラクションへの引力** — 入力欄に近づくとグローが強まる、パーティクルが入力欄に向かって流れるなど、「触ってみたい」と思わせる引力

## アニメーション設計

### 哲学

アニメーションはこのサイトの存在意義そのもの。
「パフォーマンスのためにアニメーションを削除する」は
「レストランでコスト削減のために料理を出さない」に等しい。

### やってはいけないこと

| パターン | なぜダメか |
|----------|-----------|
| 単純な `fade-in` / `slide-up` | 2010年代のWebサイトに見える。感動がない |
| `linear` イージング | 機械的で生命感がない |
| 全要素が同時に同じ動き | 不自然。合唱ではなく一人ずつが語る |
| ランダムな方向への不規則な動き | 生命感ではなくノイズ。意図が読めない |

### 求めるアニメーション品質

- **ai-breathe**: 不規則なリズムの脈動。opacity と translateY が有機的に変化
- **ai-reveal**: AIがコンテンツを生成しているかのようなスタガー出現
- **Spring physics**: バネ物理による有機的な動き（stiffness: 60, damping: 18）
- **テンプレート遷移**: clipExpand / slideOver / scaleBlur / verticalSplit を文脈で使い分け
- **退場アニメーション**: 不要になった要素は滑らかに退場する。瞬時に消えない
- **意味のある動き**: 動きが情報を伝える。近づく＝関連、離れる＝無関係、光る＝注目、暗くなる＝背景化

### 実装ルール

- **繰り返しアニメーション** → CSS `@keyframes`（compositorスレッドで実行、JSオーバーヘッド回避）
- **インタラクティブ遷移** → Framer Motion
- **GPUプロパティのみ**: `transform`, `opacity` のみアニメーション
- `background`, `filter`, `box-shadow` 等のレイアウト/ペイントプロパティのアニメーションは禁止
- `will-change` は頻繁にアニメーションする要素にのみ付与（過剰使用はメモリ浪費）

## インタラクション設計

### 会話型ナビゲーション

ユーザーの入力（自然言語テキスト）が主要な操作手段。
メニューもハンバーガーもパンくずリストも不要。

- AIが意図を分類 → データ取得 → テンプレート選択 → レンダリング
- 「プロフィール見せて」「何ができるの？」「連絡先は？」で十分
- オフトピックの質問にも人格ある応答を返す（ポートフォリオの一部として）

### 行動観察に基づくプロアクティブUI

テキスト入力だけがインタラクションではない。
ユーザーの行動そのものがサイトへの暗黙の入力:

- **滞在時間**: アイドル状態の長さに応じて段階的にヒントを提示
- **カーソル位置**: ホバー位置の近傍にある情報を予測的に強調
- **入力欄の状態**: フォーカスしたが打たない → サジェストキーワードを浮かべる
- **操作パターン**: 素早い探索的な動き → 主要要素をハイライト

これらの応答は常に**環境に溶け込む形**で行う。ポップアップ、ツールチップ、モーダルは使わない。
光が変わる、要素が近づく、新しいものがゆっくり出現する — 空間の変化として表現する。

### 状態遷移のUX

- テンプレート間の遷移は必ずアニメーションで接続する
- ローディング状態も世界観の一部として設計する（LoadingOverlay）
- エラー状態でも世界観を壊さない（StaticFallback）

### ホバー・フォーカス・展開

- ホバー認識領域は寛大に設定する（小さすぎるとUXが悪い）
- フォーカス中の要素以外はディム（視覚的フォーカスの誘導）
- 展開はインラインで行う（別パネルに飛ばさない）
- ホバー・展開時にメディア（画像・GIF）を表示可能にする

## 空間レイヤーの概念構造

背景から前景に向かう概念的な層:

1. **環境層** — グラデーションメッシュ、軌道リング。世界の基盤
2. **雰囲気層** — パーティクル、接続線、パルス。生命感の演出
3. **コンテンツ層** — テンプレートが描画される主レイヤー
4. **インタラクション層** — マウスグロー、入力フィールド
5. **オーバーレイ層** — 展開詳細、モーダル的要素

実装上の要件:
- 各層は `isolation: isolate` でスタッキングコンテキストを分離
- `contain: layout paint` でレイアウトの影響範囲を制限
- `perspective` + `rotateX/Y` 使用時はDOM描画順序とz-indexの両方で制御

---

## パフォーマンス要件

アニメーション豊富なサイトだからこそ、パフォーマンスは厳格に管理する。
60fps を下回るアニメーションは「壊れた体験」であり、アニメーションがない方がマシ。

1. **GPU合成プロパティのみアニメーション** — `transform`, `opacity`
2. **パーティクル数の動的制御** — 表示要素数に応じて削減: `Math.max(6, 12 - nodes.length)`
3. **useMemo でレイアウト計算キャッシュ** — 再レンダーごとの再計算を防止
4. **MotionValue 活用** — マウス座標等はstateではなくMotionValueで管理（不要な再レンダー防止）
5. **条件付きレンダリング** — 非表示要素はDOMに出さない
6. **CSS containment** — `contain: layout paint` でレイアウト影響範囲を隔離

## 技術的注意

- **Next.js 16 + React 19 hydration**: `mounted` パターンでSSR/クライアント差分を回避
- **Framer Motion 12**: `ease` 配列には `as const` 必須
- **3D stacking context**: `perspective` + `rotateX/Y` 使用時、DOM描画順序とz-indexの両方で制御
- **ブラウザ拡張由来のhydrationエラー**: `cz-shortcut-listen` 等はコード側の問題ではない
- **FloatingInput の `entered` パターン**: 初期エントリーアニメーションとホバー遷移を分離するため、`setTimeout` 後に `entered=true` で別のtransitionに切り替える

## 成功基準

訪問者がこのサイトを体験して:

1. **「これは普通のWebサイトではない」** と直感的に感じる
2. **説明なしで使える** — テキストで操作方法を教えなくても、視覚と行動観察だけで伝わる
3. **従来のサイトより便利だと感じる** — 見た目が違うだけでなく、体験として優れている
4. **何度訪問しても新鮮に感じる** — 毎回異なるビジュアルと応答
5. **ポートフォリオの内容が正しく伝わる** — 演出に溺れて情報が伝わらないのは本末転倒
6. **「この人は未来のUXを考えられる人だ」** と採用担当者・クライアントが思う

6番が最終目標。1〜5はそのための手段。
「見た目が未来的」は1番を満たすだけ。2〜5を満たして初めて6番に到達する。
